# 모의평가 답변

## 기본 개념

### 포트

- 서버 안에는 요청을 기다리는 프로그램이 여러 개 있다. 요청에 붙은 포트 번호를 보고 어느 프로그램에게 갈지 정해진다.
- 이번 실습에서 쓴 포트: 80번은 웹 서버 Nginx, 22번은 SSH.

### 보안 그룹과 인바운드 규칙

- 보안 그룹은 어떤 포트로 오는 요청을 서버에 들여보낼지 정한다.
- 인바운드 규칙은 밖에서 서버로 들어오는 요청 중 무엇을 들여보낼지 정한 목록이다.
- 각 규칙의 "소스" 칸으로 누가 들어올 수 있는지 정한다.
  - `0.0.0.0/0`: 세상의 모든 주소. 콘솔에서 "어디서든"을 고르면 들어간다.
  - `/32`: 딱 주소 하나. 콘솔에서 "내 IP"를 고르면 AWS가 지금 접속한 컴퓨터 주소를 `/32`로 넣어 준다.

### 화이트리스트

- 목록에 적힌 것만 허용하고, 나머지는 전부 막는 방식이다.
- 보안 그룹에는 "이건 막아라"라는 규칙이 따로 없고, 허용할 것만 적는다. 그래서 목록이 짧을수록 열린 곳이 적어진다.

### 인터넷 게이트웨이

- VPC와 인터넷을 연결해 주는 AWS 부품이다.
- VPC는 원래 인터넷과 끊겨 있어서, 이걸 붙여야 인터넷과 데이터를 주고받을 수 있다.
- 붙이기만 하면 안 되고, 라우팅 테이블에 `0.0.0.0/0 → 인터넷 게이트웨이` 줄도 있어야 길이 이어진다.

### 라우팅 테이블

- 서브넷에서 나가는 데이터가 어디로 갈지 적어 둔 표다.
- `10.0.0.0/16 → local`: VPC 안으로 가는 건 안에서 처리한다.
- `0.0.0.0/0 → 인터넷 게이트웨이`: 그 밖의 모든 곳은 인터넷 게이트웨이로 보낸다.

### 루트 사용자와 IAM 사용자

- 루트 사용자: AWS 계정을 처음 만들 때 쓴 이메일로 로그인한다. 무엇이든 할 수 있고, 권한을 줄일 수 없다.
- IAM 사용자: 루트 사용자가 계정 안에 따로 만든 사용자다. 처음에는 권한이 없고, 정책을 붙여서 할 수 있는 일을 하나씩 허락한다. 실습용 `codyssey-b3-1-student`가 이 경우다.
- IAM 역할: 사람이 아니라 서버나 프로그램이 잠깐 빌려 쓰는 권한이다. 이번 실습에서는 쓰지 않았다.

### 최소 권한

- 필요한 일만 할 수 있게 허락하는 것이다.
- 실수하거나 로그인 정보가 새어 나가도 피해를 작게 만들기 위해 필요하다.

### SSH

SSH는 내 컴퓨터에서 멀리 있는 서버에 접속해 명령어를 치게 해 주는 방법이다.

- 왜 필요한가: EC2 서버는 AWS 데이터센터에 있어서 모니터나 키보드를 직접 꽂을 수 없다. 그래서 Mac 터미널에서 SSH로 접속한 뒤, 서버에서 Nginx 설치 같은 명령어를 쳤다.
- 접속 명령어: `ssh -i 키파일 ec2-user@서버주소`
  - `ssh`: SSH로 접속하겠다는 명령어
  - `-i 키파일`: 내가 누구인지 증명할 키 파일
  - `ec2-user`: 서버 안의 사용자 이름 (Amazon Linux 기본 사용자)
  - `서버주소`: 서버의 공인 IP
- 이 요청은 서버의 22번 포트로 간다. 서버 안에서는 SSH 프로그램이 22번 포트로 오는 요청을 기다린다.
- 키는 두 개가 한 쌍이다.
  - 공개 키: 서버가 가지고 있다. EC2를 만들 때 키 페어를 고르면 AWS가 서버에 넣어 준다.
  - 개인 키: Mac에 있는 `.pem` 파일이다. 나만 가지고 있어야 한다.
- 접속할 때 서버는 "이 공개 키와 짝이 맞는 개인 키를 가졌는지 증명해 봐"라고 묻는다. Mac이 개인 키로 증명하면 들어갈 수 있다. 개인 키 파일 자체는 서버로 보내지 않는다.
- 조심할 점
  - 개인 키가 새어 나가면 누구나 서버에 들어올 수 있다. 그래서 `.pem` 파일은 레포에 올리지 않았다.
  - 22번 포트를 내 주소 하나로 막아 두면, 키가 없는 사람은 로그인 단계까지 오지도 못한다.
  - 접속이 되면 통신 내용은 암호화되어서, 중간에서 엿봐도 내용을 읽을 수 없다.

## B3-1-E06

> 외부 → IGW → Subnet → EC2로 이어지는 네트워크 흐름을 다이어그램 기준으로 설명할 수 있는가?

## B3-1-E07

> 보안 그룹 규칙을 어떤 기준으로 최소화했는지(허용/미허용 포트) 설명할 수 있는가?

네, E03의 인바운드 규칙 화면을 보면서 설명드리겠습니다.

먼저 포트를 짧게 말씀드리면, 서버 안에는 요청을 기다리는 프로그램이 여러 개 있습니다. 요청에 붙은 포트 번호를 보고 어느 프로그램에게 갈지 정해집니다. 보안 그룹은 어떤 포트로 오는 요청을 들여보낼지 정합니다. 그중 인바운드 규칙은 밖에서 서버로 들어오는 요청 중 무엇을 들여보낼지 정한 목록입니다.

이 목록은 화이트리스트 방식입니다. 화이트리스트는 "목록에 적힌 것만 허용하고, 나머지는 전부 막는다"는 뜻입니다. 보안 그룹에는 "이건 막아라"라는 규칙이 따로 없고, 허용할 것만 적습니다. 그래서 목록이 짧을수록 열린 곳이 적어집니다.

제 기준은 "꼭 필요한 포트만 적는다"였습니다. 그래서 인바운드 규칙은 두 개뿐입니다. 누가 들어올 수 있는지는 각 규칙의 "소스" 칸으로 정했습니다.

첫째는 80번 포트입니다. 웹 서버인 Nginx가 받는 포트입니다. 웹사이트는 모두가 봐야 하니까, 소스를 "어디서든"으로 골랐습니다. 그러면 소스가 0.0.0.0/0이 되는데, 세상의 모든 주소라는 뜻입니다.

둘째는 22번 포트입니다. 서버에 원격으로 접속하는 SSH가 받는 포트입니다. 관리는 저만 하면 되니까, 소스를 "내 IP"로 골랐습니다. 그러면 AWS가 지금 접속한 제 컴퓨터의 주소를 슬래시 32로 자동으로 넣어 줍니다. 슬래시 32는 딱 그 주소 하나라는 뜻입니다.

나머지 포트는 목록에 적지 않았으니 자동으로 막힙니다. 데이터베이스 포트나 다른 포트는 이번 실습에서 쓰지 않기 때문입니다. 모든 포트를 한꺼번에 여는 규칙도 만들지 않았습니다.

## B3-1-E08

저는 B를 주로 썼고, A도 해 봤습니다. B는 다른 분들 사례를 보고 골랐습니다. 해 보니 B가 더 확실했습니다. 항상 "OK"라는 똑같은 답이 와서, 성공했는지 바로 알 수 있었기 때문입니다.

## B3-1-E10

> Public Subnet Route Table의 기본 경로(0.0.0.0/0 → IGW)가 필요한 이유를 설명할 수 있는가?

네, 그림의 라우팅 테이블을 보면서 말씀드리겠습니다.

먼저 인터넷 게이트웨이는 VPC와 인터넷을 연결해 주는 AWS 부품입니다. VPC는 원래 인터넷과 끊겨 있어서, 이걸 붙여야 인터넷과 데이터를 주고받을 수 있습니다.

라우팅 테이블은 서버에서 나가는 데이터가 어디로 갈지 적어 둔 표입니다. 줄이 두 개 있습니다.

첫 줄은 "VPC 안으로 가는 건 안에서 처리해라"입니다.
두 번째 줄은 "그 밖의 모든 곳은 인터넷 게이트웨이로 보내라"입니다.

제 노트북은 VPC 밖에 있습니다. 그래서 서버가 제 노트북에 답을 보낼 때 이 두 번째 줄을 따라갑니다.

이 줄이 없으면 인터넷 게이트웨이를 붙여 놨어도 서버는 거기로 가는 길을 모릅니다. 요청은 들어와도 답을 못 돌려보내서 페이지가 안 뜹니다.

그래서 이 줄이 꼭 있어야 합니다. 이상입니다.

## B3-1-E11

> Security Group과 IAM의 책임 범위 차이를 설명하고, 최소 권한이 왜 필요한지 설명할 수 있는가?

네, 보안 그룹 규칙 화면과 IAM 정책 파일을 보면서 말씀드리겠습니다.

둘 다 "막는 것"이지만, 막는 대상이 다릅니다.

보안 그룹은 **서버로 들어오는 접속**을 막습니다. 저는 웹용 80번 포트와 제 컴퓨터에서 오는 SSH 22번 포트만 열었습니다.

IAM은 **AWS 계정 안에서 사람이 할 수 있는 일**을 막습니다. 누가 서버를 만들고, 누가 지울 수 있는지를 정합니다.

그래서 보안 그룹은 서버를 지키고, IAM은 AWS 계정을 지킵니다.

AWS 계정에는 두 종류의 사용자가 있습니다. 루트 사용자는 계정을 만든 이메일로 로그인하고, 무엇이든 할 수 있습니다. IAM 사용자는 계정 안에 따로 만든 사용자이고, 허락한 일만 할 수 있습니다. 그래서 실습 작업은 IAM 사용자로 했습니다.

최소 권한은 "필요한 일만 할 수 있게 허락한다"는 뜻입니다. 제 실습용 사용자에게는 이번 실습에 필요한 권한만 줬습니다. 서울 리전에서만 쓸 수 있고, 작은 서버만 만들 수 있고, 지우는 것도 이번 실습 리소스만 지울 수 있습니다.

이게 필요한 이유는, 실수하거나 로그인 정보가 새어 나가도 피해를 작게 만들기 위해서입니다. 권한이 다 있으면 큰 서버를 잔뜩 만들어 돈이 나가거나, 다른 리소스를 지울 수도 있습니다.

실제로 처음에는 보안 그룹을 만들 권한이 없어서 오류가 났습니다. 그때도 전부 열지 않고 그 권한 하나만 추가했습니다. 이 과정은 트러블슈팅 문서에 있습니다. 이상입니다.

## B3-1-E12

> SSH(22) 또는 DB 포트를 0.0.0.0/0로 열면 안 되는 이유와 대안을 설명할 수 있는가?

네, E03의 인바운드 규칙 화면을 보면서 말씀드리겠습니다.

SSH는 제 컴퓨터에서 서버에 접속해서 명령어를 치게 해 주는 방법이고, 서버의 22번 포트로 들어갑니다. 들어갈 때는 제 Mac에 있는 개인 키로 제가 맞는지 증명합니다.

0.0.0.0/0은 세상의 모든 주소라는 뜻입니다. 서버로 오는 요청에는 보낸 사람 주소가 적혀 있고, 보안 그룹은 이 주소를 규칙과 맞춰 봅니다. 그런데 22번 포트의 소스가 0.0.0.0/0이면 누가 보냈든 통과합니다. 그래서 아무나 제 서버 주소로 SSH를 치면 로그인 단계까지 옵니다.

키가 없으면 들어오지는 못합니다. 하지만 인터넷에는 열린 포트를 자동으로 찾아다니는 프로그램이 많아서, 22번이 열려 있으면 계속 로그인을 시도합니다. 뚫리면 남이 제 서버를 마음대로 쓰게 됩니다.

DB 포트를 열어도 마찬가지로 공격을 받고, 안에 있는 데이터가 새어 나가거나 지워질 수 있습니다.

대안은 들어올 수 있는 곳을 좁히는 겁니다. SSH는 제 컴퓨터 주소 하나만 허용하면 됩니다. 저도 소스를 "내 IP"로 골라서 슬래시 32, 주소 하나만 들어오게 했습니다. 이러면 다른 사람이 보낸 요청은 보안 그룹에서 버려져서, 로그인 단계까지 오지도 못합니다.

DB는 인터넷에 열지 않고, DB를 쓰는 웹 서버에서 오는 접속만 허용하면 됩니다. 이번 실습에는 DB가 없어서 DB 포트는 열지 않았습니다. 이상입니다.

## B3-1-E13

> 트러블슈팅에서 가설 → 검증 순서를 유지한 이유와, 로그/근거를 어떻게 활용했는지 설명할 수 있는가?

네, 트러블슈팅 문서를 보면서 말씀드리겠습니다.

제 사례는 실습용 사용자로 보안 그룹을 만들다가 오류가 난 것입니다.

1. **근거**: 오류 메시지에 "보안 그룹을 만들 권한이 없다"고 권한 이름까지 적혀 있었습니다.
2. **가설**: 설정 문제가 아니라 권한 문제라고 추측했습니다. 그래서 다시 시도 버튼은 누르지 않았습니다.
3. **검증**: 로그인한 사용자와 리전을 확인하고, 정책 파일을 열어 보니 그 권한이 정말 없었습니다.
4. **해결**: 그 권한만 추가했습니다.
5. **확인**: 같은 설정으로 다시 만들었더니 성공했습니다.

NAT 게이트웨이 조회 권한이 없다는 오류도 있었습니다. 이건 하려던 작업을 막지 않아서 권한을 늘리지 않았습니다.

이상입니다.
